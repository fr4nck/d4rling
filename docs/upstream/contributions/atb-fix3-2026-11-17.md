## Défaut (SRC, amont `0a4c55eb`)

`AudioFileFormatManager::analyzeAudioFileComponent` lit `CanRead` et
`CanWrite` avec `propSize = sizeof(UInt32)`, puis lit les trois propriétés
`kAudioFileComponent_UTIsForType`, `_MIMETypesForType` et
`_ExtensionsForType` sans remettre `propSize` à la taille d'un `CFArrayRef`.
Le composant exige l'égalité stricte
(`AudioFileComponentBase.cpp`, `if (*ioPropertySize != sizeof(CFArrayRef)) return kAudioFileBadPropertySizeError;`).

- En 64 bits, 4 ≠ 8 : les trois tables de chaque composant restent vides.
- En 32 bits, 4 = 4 : cela fonctionne par hasard.

Ces tables alimentent `kAudioFileGlobalInfo_*ForType`, `_All*` et
`_TypesFor*` (`AudioFile.cpp`, cas 518-590), ainsi que le choix du type
d'après l'extension à l'ouverture sans indice (`AudioFile.cpp:93`).

## Brouillon de PR (anglais)

**Title:** `AudioToolbox: read the AudioFile component string arrays with a pointer size`

> `AudioFileFormatManager` queries each AudioFile component for its UTIs, MIME types and file extensions, which come back as a `CFArrayRef`. It reused the `propSize` left at `sizeof(UInt32)` by the `CanRead`/`CanWrite` queries, and `AudioFileComponentBase` rejects any size other than `sizeof(CFArrayRef)`. In a 64-bit process the three tables of every component therefore stayed empty: `kAudioFileGlobalInfo_ExtensionsForType`, `_UTIsForType`, `_MIMETypesForType` and the `_All*` lists returned empty arrays, and opening a file without a type hint could not use its extension. 32-bit processes worked only because a pointer is 4 bytes there.
>
> ## Changes
> - Set `propSize` to `sizeof(CFArrayRef)` before each of the three queries.
> - `tests/src/audiofile_type_tables.c` checks the usual extensions of WAVE, AIFF, AIFF-C and CAF, the WAVE UTI and its RFC 2361 MIME type, that every readable type answers the three properties with values found in the matching global list, and that an unknown type or a short specifier is refused.
>
> ## Testing
> *(to be completed after running on an upstream build)* Tested under Darling on x86_64 and i386: `audiofile_type_tables` fails on x86_64 without the change (empty tables) and passes on both architectures with it; on i386 it passes before and after.
>
> ## Provenance
> The public `AudioFile.h` documentation of the `kAudioFileGlobalInfo_*` properties, the UTI Apple declares for WAVE audio, RFC 2361 for the MIME type, and the Darling sources involved. No Apple binary was disassembled, no restricted material was used, no code was copied from another project, and there are no new dependencies. Prepared with the help of an AI assistant; I have reviewed the change and can explain it.

## Défaut voisin, hors de cette PR : ATB-FIX4 (`TypesFor*`)

AudioFile.h décrit le spécificateur de `kAudioFileGlobalInfo_TypesForExtension`,
`_TypesForUTI` et `_TypesForMIMEType` comme « a CFStringRef ». Des programmes
macOS publics passent l'adresse de ce `CFStringRef` avec `sizeof(CFStringRef)`,
comme pour les autres spécificateurs :
[qaac `AudioFileX.h`](https://github.com/nu774/qaac/blob/master/AudioFileX.h),
[SFBAudioEngine `SFBCoreAudioEncoder.mm`](https://github.com/sbooth/SFBAudioEngine/blob/main/Sources/CSFBAudioEngine/Encoders/SFBCoreAudioEncoder.mm),
[DOUAudioStreamer `DOUAudioFileProvider.m`](https://github.com/douban/DOUAudioStreamer/blob/master/src/DOUAudioFileProvider.m).
Darling (fork et amont) lit `inSpecifier` comme la chaîne elle-même
(`static_cast<CFStringRef>(inSpecifier)`). Avec la convention de ces
programmes, le témoin plante (SIGSEGV, rc 139) à la première recherche, avec
ou sans ATB-FIX3, en i386 comme en x86_64 (8/8 essais le 17/11). Les essais
`k*` du 15/11 avaient fait le même constat, mais l'avaient attribué au témoin.
`CFStringGetCStringPtr`, qui peut rendre `NULL`, est un second point fragile.

Statut : **INF fort, non corrigé**. La convention d'appel n'a pas été observée
sur macOS dans ce lot. Un dossier séparé est à prévoir, avec un test
d'aller-retour ; une première version de ce test existe dans l'historique du
lot, mais n'est pas publiée.
