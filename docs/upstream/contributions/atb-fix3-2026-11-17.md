## Défauts (SRC)

**ATB-FIX3.** `AudioFileFormatManager::analyzeAudioFileComponent` lit les
propriétés `kAudioFileComponent_UTIsForType`, `_MIMETypesForType` et
`_ExtensionsForType` (des `CFArrayRef`) avec le `propSize = sizeof(UInt32)`
laissé par `CanRead`/`CanWrite`. Or `AudioFileComponentBase.cpp` exige
`*ioPropertySize == sizeof(CFArrayRef)`. En 64 bits, les tables de chaque
composant restent vides : `kAudioFileGlobalInfo_*ForType` et `_All*` sont vides,
et l'ouverture sans indice ne peut pas s'appuyer sur l'extension
(`AudioFile.cpp:93`). En 32 bits, cela fonctionne par hasard (4 = 4).

**ATB-FIX4.** `kAudioFileGlobalInfo_TypesForExtension`, `_TypesForUTI` et
`_TypesForMIMEType` traitaient le pointeur de spécificateur comme le
`CFStringRef` lui-même. Selon la documentation publique de `AudioFile.h`,
*« A specifier is a buffer of data »* et `inSpecifierSize` est *« the size of
the specifier data »* : le tampon contient le `CFStringRef`. C'est aussi
l'usage de [qaac](https://github.com/nu774/qaac/blob/master/AudioFileX.h),
[SFBAudioEngine](https://github.com/sbooth/SFBAudioEngine/blob/main/Sources/CSFBAudioEngine/Encoders/SFBCoreAudioEncoder.mm)
et [DOUAudioStreamer](https://github.com/douban/DOUAudioStreamer/blob/master/src/DOUAudioFileProvider.m).
De plus, la clé venait de `CFStringGetCStringPtr`, qui rend `NULL` pour une
chaîne non ASCII ; un `std::string` était alors construit à partir de `NULL`.

## Brouillons de PR (anglais)

### PR 1 — `AudioToolbox: read the AudioFile component string arrays with a pointer size`

> `AudioFileFormatManager` queries each AudioFile component for its UTIs, MIME types and file extensions, which come back as a `CFArrayRef`. It reused the `propSize` left at `sizeof(UInt32)` by the `CanRead`/`CanWrite` queries, and `AudioFileComponentBase` rejects any size other than `sizeof(CFArrayRef)`. In a 64-bit process the three tables of every component stayed empty: `kAudioFileGlobalInfo_ExtensionsForType`, `_UTIsForType`, `_MIMETypesForType` and the `_All*` lists returned empty arrays, and opening a file without a type hint could not use its extension. 32-bit processes worked only because a pointer is 4 bytes there.
>
> ## Changes
> - Set `propSize` to `sizeof(CFArrayRef)` before each of the three queries.
> - `tests/src/audiofile_type_tables.c` checks the usual extensions of WAVE, AIFF, AIFF-C and CAF, the WAVE UTI and its RFC 2361 MIME type, that every readable type answers the three properties with values found in the matching global list, and that an unknown type or a short specifier is refused.
>
> ## Testing
> Tested under Darling on x86_64 and i386, on a build of master with the change:
> - `audiofile_type_tables` fails on x86_64 without the change (7 missing values, 3 empty global lists) and passes on both architectures with it; on i386 it passes before and after.
> - `audiofile_pcm` (with `tests/coreaudio/pcm-fixtures`) and `audioconverter_pcm` pass on both architectures, as before the change.
>
> ## Provenance
> The public `AudioFile.h` documentation of the `kAudioFileGlobalInfo_*` properties, the UTI Apple declares for WAVE audio, RFC 2361 for the MIME type, and the Darling sources involved. No Apple binary was disassembled, no restricted material was used, no code was copied from another project, and there are no new dependencies. Prepared with the help of an AI assistant; I have reviewed the change and can explain it.

### PR 2 — `AudioToolbox: read the CFStringRef held by the TypesFor* specifiers` (depends on PR 1)

> `kAudioFileGlobalInfo_TypesForExtension`, `_TypesForUTI` and `_TypesForMIMEType` treated the specifier pointer as the `CFStringRef` itself. `AudioFile.h` documents a specifier as a buffer of data of `inSpecifierSize` bytes, so for these properties it holds a `CFStringRef`, as programs pass it (`sizeof(CFStringRef)` and the address of the string); Darling read that address as a string object and crashed. The key was also taken from `CFStringGetCStringPtr()`, which may return NULL, and does for a string that is not ASCII.
>
> ## Changes
> - Read the `CFStringRef` from the specifier buffer; a missing specifier or a wrong size is `kAudioFileBadPropertySizeError`, a NULL string `kAudio_ParamError`.
> - Copy the string with `CFStringGetCString()` when `CFStringGetCStringPtr()` returns NULL.
> - `tests/src/audiofile_types_for_strings.c` checks the documented inverse of `ExtensionsForType`, `UTIsForType` and `MIMETypesForType` for every readable type, well-known values, strings made from UTF-16 characters including one that is not ASCII, and bad specifiers.
>
> ## Testing
> Tested under Darling on x86_64 and i386, on a build of master with PR 1 and this change:
> - `audiofile_types_for_strings` crashes on both architectures without the change and passes with it. Reading the pointer correctly but keeping `CFStringGetCStringPtr()` alone still crashes on the non-ASCII extension.
> - `audiofile_type_tables`, `audiofile_pcm` and `audioconverter_pcm` pass on both architectures.
> - No exported symbol is added.
>
> ## Provenance
> The public `AudioFile.h` documentation of `AudioFileGetGlobalInfo` and of the `TypesFor*` properties, the CoreFoundation documentation of `CFStringGetCStringPtr`, and the calling convention visible in open-source macOS programs (qaac, SFBAudioEngine, DOUAudioStreamer), whose code was only read, not copied. No Apple binary was disassembled, no restricted material was used, and there are no new dependencies. Prepared with the help of an AI assistant; I have reviewed the change and can explain it.
