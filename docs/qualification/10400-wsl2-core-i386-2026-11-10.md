## Target-inventory result and source-level identification

On the 10400, both the `cmake --build "$BUILD" --target help` and
`ninja -C "$BUILD" -t targets all` inventories completed. The filtered
terminal excerpts matched mainly **paths** under
`src/external/xnu/darling/src/libsystem_kernel`, and therefore did not
identify the top-level target names. **The failure remains a name/target
selection problem, not evidence of a failed CoreFoundation compiler.**

Further GitHub source inspection of the **pinned** submodules identified:
`darling-corefoundation` at
`a3640a77410cf1825f7855172b1551ae7917c461` invokes
`add_separated_framework(CoreFoundation ...)`. The historical CMake macro
creates `CoreFoundation_i386` and `CoreFoundation_x86_64` as build
targets, while `CoreFoundation` itself is an **IMPORTED** library target.
Similarly, the pinned libc and libsystem CMake files define `system_c`
and `system`. These identities are **source-derived only** until their
presence is queried in the generated 10400 Ninja tree.

## First genuine Darwin i386 guest execution PASS (2026-11-10)

**This is an operator-provided terminal result, not CI.** On the same
i5-10400, the historical source and private core install were used to
rebuild the Carbon event/parameter witness:

~~~text
CARBON_I386_PROBE_BUILD=PASS
RUNTIME_EXECUTED=NO
~~~

`file` reported:

- `carbon-probe/carbon-dynamic-i386`: **Mach-O i386 executable**;
- `carbon-probe/libD4CarbonEvents.dylib`: **Mach-O i386 shared library**.

`llvm-lipo-19 -archs` confirmed `i386` for the executable. The
operator then invoked the repository's `reproduction/run-guest.sh` with
mode `normal` and a 20-second timeout, with the existing private
installation. The wrapper uses `unshare` user/mount/PID/IPC/UTS/network
namespaces and a fresh prefix; this run satisfied its namespace assertions.

The output was:

~~~text
REPORT=/tmp/d4rl-replay.3pBmFjCD
EXIT_CODE=0
~~~

`stdout.log` contained exactly:

~~~text
D4RLING-CARBON-EVENT-I386-OK
~~~

The operator's verification checked the **exit code and stdout marker**
together, producing `PASS : execution Carbon i386`.

`stderr.log` reported seven
`sh: 1: xdg-user-dir: not found` messages, then
`Warning: failed to increase FD rlimit: Operation not permitted`.
Neither prevented this witness from completing; neither is claimed
resolved or harmless for arbitrary other guests.

**Qualified claim:** the historical **i386 Mach-O Carbon witness ran
successfully on the 10400 under an isolated Darling guest**. This is
runtime evidence, not a general compatibility or audio result.
It does **not** establish mode `bypass`, the missing-dylib negative
control, current `master`, QuickTime or Logic Studio 8.
