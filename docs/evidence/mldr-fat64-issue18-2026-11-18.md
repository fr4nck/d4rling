# mldr — FAT32/FAT64 bornés : port de Darling #2069 sur `master` (18 novembre 2026)

**TEST invité i386/x86_64 sur le 5700X**, par le vrai chemin de chargement de
mldr. Suite de l'[issue #18](https://github.com/fr4nck/d4rling/issues/18).

Effets :
- les quatre magics universels sont reconnus (FAT32 et FAT64, gros- et
  petit-boutistes) ;
- `nfat_arch` est plafonné à 64 ;
- la table et chaque tranche doivent tenir dans le fichier ;
- un enregistrement invalide est ignoré sans masquer un enregistrement valide ;
- un `offset` non représentable en `off_t` est refusé avant `lseek`. En
  `mldr32` (sans `_FILE_OFFSET_BITS=64`), c'est le cas au-delà de 2 Gio.

**Préservé.** Le diff ne touche ni l'appel `open(path, O_RDONLY | O_CLOEXEC)`
(`860dee49`), ni les gardes i386, ni le diagnostic `D4RLING_MLDR_I386_MMAP_DIAG`,
ni `code_signing_gate()` (`uint64_t`, conversion depuis `off_t` sans perte).

**Patch privé de l'issue.** Le patch `f769b8b0…` (SHA-256 vérifié), préparé sur
P09 `4be2603c`, n'a pas été appliqué tel quel :
- il réinsérait `O_CLOEXEC`, déjà sur `master` ;
- il reformatait `load_fat` en espaces ;
- il supprimait deux commentaires amont.

Les hunks amont s'appliquent directement sur `master`. La différence avec le
patch privé se limite aux espaces et à ces deux commentaires (`diff -w`) : la
sémantique est identique.

## Base et méthode

- Base : `master` `1a6bfc32`. Le dossier `src/startup/mldr` de B13 + `O_CLOEXEC`
  est identique à celui de `master` : 35 blobs égaux et 18 liens symboliques.
- `mldr` et `mldr32` sont reconstruits avec les commandes Ninja de B13, en
  lecture seule. `mldr.c` (qui inclut `loader.c`) et `fat_slice.c` sont compilés
  depuis une copie privée, les autres objets viennent de B13.
- La référence reconstruite a les mêmes sections `.text`, `.rodata` et `.data`
  que les binaires `O_CLOEXEC` déjà qualifiés : la méthode est fidèle.
- `fat_slice.c` compile sans avertissement. La variante
  `-DD4RLING_MLDR_I386_MMAP_DIAG` compile aussi : `mldr32` change, `mldr` 64
  bits reste identique, comme attendu.
- Le candidat n'ajoute que `mldr_fat_is_magic` et `mldr_fat_select`.
  `load()` garde son unique `open(…, 0x80000)` (`O_CLOEXEC`), dans les quatre
  binaires.
- B13, P09, P03 et l'installation privée n'ont pas été modifiés : empreintes
  identiques avant et après, aucun fichier plus récent que le début du lot.

## Invité réel

Le banc R5 est utilisé :
- user namespace délégué, avec namespaces mount, pid et net privés ;
- installation en lecture seule et préfixe neuf à chaque exécution ;
- `mldr`/`mldr32` (et `dyld` quand il varie) substitués par une couche overlay
  du namespace ;
- délai de 60 s.

Le témoin [`fatprobe.m`](../../tests/regressions/mldr-fat64/fatprobe.m) affiche
l'architecture exécutée. 54 exécutions, dont une invalide (dossier de préfixes
absent, aucun programme lancé).

**Par `dyld`.** mldr charge `dyld` lui-même. Le `dyld` installé est un universel
FAT32 i386 + x86_64 : chaque exécution passe donc par `load_fat`, dans `mldr`
puis dans `mldr32`. Ses variantes d'en-tête gardent des tranches identiques à
l'octet ([`makedyld.py`](../../tests/regressions/mldr-fat64/makedyld.py)).

| `dyld` | `master` i386 / x86_64 | **candidat** i386 / x86_64 |
| --- | --- | --- |
| FAT32 d'origine | PASS / PASS | PASS / PASS |
| **FAT64 gros-boutiste** | conteneur bloqué / bloqué | **PASS / PASS** (×2) |
| **FAT64 petit-boutiste** | bloqué / bloqué | **PASS / PASS** (×2) |
| FAT32 petit-boutiste | PASS / PASS | PASS / PASS |
| `nfat_arch = 0xffffffff` | bloqué / bloqué | refusé / refusé |
| tranche x86_64 hors du fichier | PASS / PASS (taille ignorée) | refusé / refusé |

« Bloqué » et « refusé » : le premier processus du conteneur ne démarre pas
(`Timed out waiting for shellspawn`). Le candidat est plus strict qu'avant : un
`dyld` dont une tranche déborde du fichier est maintenant refusé.

**Par `execve`.** Les exécutables universels sont générés par
[`makefat.py`](../../tests/regressions/mldr-fat64/makefat.py).

| Exécutable | `master` | **candidat** |
| --- | --- | --- |
| FAT32 i386 + x86_64 | x86_64 | x86_64 (×2) |
| FAT32 i386 seul | i386 | i386 (×2) |
| **FAT32, x86_64 hors du fichier + i386 valide** | **SIGSEGV (rc 139) ×2** | **i386, rc 0 (×2)** |
| FAT32, `nfat_arch = 0xffffffff` | `Cannot read fat_arch header.` | `Malformed fat file header.` |
| FAT64 (4 variantes) | rc 1 | rc 1 — voir limites |

Aucun processus résiduel et aucun montage restant (38 avant et après).
L'installation est intacte.

## Limites

- **Un exécutable FAT64 lancé par `execve` n'atteint pas mldr**, ni ici ni dans
  Darling officiel. L'`execve` émulé du sous-module xnu ne reconnaît que
  `FAT_MAGIC`/`FAT_CIGAM` (`execve.c`, ligne 223 ; même code dans
  `darlinghq/darling-xnu`). Le corriger demande de modifier le gitlink xnu, gelé
  jusqu'à l'alignement C7 : ce n'est pas fait ici. Le chemin FAT64 de mldr est
  qualifié par `dyld`.
- `mldr32` refuse une tranche au-delà de 2 Gio, comme l'amont.
- Aucun binaire Apple propriétaire n'est utilisé. Pas de SoundHack ni de Logic.

## Décision

**Intégré** :
- la porte de l'issue est satisfaite : rebase sur `master`, tests amont et
  négatifs, builds i386 et x86_64 sur la nouvelle base, contrôle des symboles et
  de `O_CLOEXEC` ;
- l'invité montre un **défaut réel corrigé** : SIGSEGV de `master` sur une
  table FAT32 malformée ;
- il montre aussi le **gain FAT64** par `dyld`, sans régression sur FAT32 ;
- le port suit l'amont à l'identique.

Statuts :
- `FAT32_GUEST=PASS` ;
- `FAT64_GUEST_VIA_DYLD=PASS` ;
- `FAT64_EXEC_VIA_EXECVE=NOT_REACHABLE (xnu execve, hors périmètre)` ;
- `UPSTREAM=déjà présent (#2069)`, aucun reversement nécessaire.
