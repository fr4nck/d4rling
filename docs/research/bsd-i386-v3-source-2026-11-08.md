# BSD Darwin i386 — V3 et candidat source

**8 novembre 2026 — R-A1/R-A2, suivi [issue #11](https://github.com/fr4nck/d4rling/issues/11).**
V3 confirme l'effet du candidat binaire B7 sur les erreurs des appels testés
dans `libsystem_kernel.dylib`. Un candidat source distinct passe ensuite
deux séries de **82 659 contrôles chacune**, dans un témoin Mach-O i386 avec
gestionnaires synthétiques. **La bibliothèque système reconstruite et le
dyld intégré restent à qualifier.**

## V3 — erreurs sur les vrais appels, bibliothèque identifiée en mémoire

| Exécution conservée | Bibliothèque i386 identifiée | Code | V3_ERRORS |
| --- | --- | ---: | ---: |
| Référence 1 | Originale | 10 | 6 |
| Candidat 1 | B7 | 0 | 0 |
| Référence 2 | Originale | 10 | 6 |
| Candidat 2 | B7 | 0 | 0 |

Sur le chemin absent, `access`, `stat64` et `lstat64` passent de
`-2 / errno=0` à `-1 / errno=2` ; `realpath` passe de `NULL / errno=0` à
`NULL / errno=2`. `getattrlist` retourne `-22 / errno=0` en référence,
`-1 / errno=22` avec B7, sur `/` comme sur le chemin absent. **Seule sa
convention d'erreur est validée ; son succès reste ouvert.**

Sur `/`, les succès affichés d'`access`, `stat64`, `lstat64` et `realpath`
ont été lus dans les journaux ; ils ne sont pas tous comptés automatiquement
par `V3_ERRORS`. Le zéro du témoin ne qualifie donc pas tous les positifs.

Les deux séquences de 24 octets aux offsets fichier `0x49387` et `0x4939f`
ont été comparées aux binaires archivés pour chacune des quatre exécutions.
La bibliothèque mappée provient de la vue du préfixe, pas nécessairement
du fichier que l'on monte isolément dans l'installation. Le premier montage
d'un fichier B7 laissait les octets originaux en mémoire : ces anciens
essais ne sont pas une contre-preuve de B7.

La méthode concluante utilise une installation privée, remplacement de
l'entrée candidate par nouveau fichier puis `os.replace`, montage de
l'installation entière en lecture seule dans les namespaces privés et
préfixe neuf par essai. Les fichiers partagés par liens physiques ne sont
jamais écrits en place.

## Candidat source — CF/EAX, appels inconnus et retours larges

Le [patch](../../reproduction/patches/bsd-i386-return-fa29287.patch) change
uniquement `bsd_syscall.S`, `bsd_syscall_table.h` et `bsd_syscall_table.c`
du composant xnu. Il est publié comme artefact de recherche ; le sous-module
et les fichiers de production du dépôt ne reçoivent pas ce patch.

La sortie i386 restaure la pile puis construit explicitement le statut
Darwin : erreur dans la plage réservée `-4095..-1`, EAX positif et CF=1 ;
sinon résultat conservé et CF=0. Un simple test du signe serait incorrect
pour des adresses ou d'autres valeurs dont le bit haut est posé.

L'inventaire des 268 entrées de table et de leurs déclarations C identifie
`sys_lseek` (199) comme seul retour C `long long` de cette révision. Pour cet
appel, le mot haut EDX doit aussi valoir `0xffffffff` avant de classer le mot
bas comme erreur. Les motifs `0x00000000ffffffff` et `0x7fffffffffffffff`
ne sont donc pas confondus avec `-1`. Les retours C 32 bits ignorent EDX,
dont la valeur n'est pas garantie par leur ABI.

Le numéro d'appel masqué est conservé dans 16 octets de pile supplémentaires,
sans changer l'alignement des appels C ni les 14 arguments copiés. `.no_sys`
reçoit maintenant ce numéro, au lieu de l'adresse de la table, avec un
alignement C correct et la même conversion d'erreur. La borne de la table
est vérifiée avant lecture ; sa taille 600 est définie une seule fois dans
un en-tête partagé C/assembleur. Les plages de hooks de sept octets restent
présentes et les objets compilés du dispatcher x86_64 sont identiques.

## Test du dispatcher compilé

| Variante | Code | Contrôles | Échecs |
| --- | ---: | ---: | ---: |
| Source originale, indices hors table omis | 10 | 82 641 | 36 863 |
| Candidat 1 | 0 | 82 659 | 0 |
| Contre-épreuve synthétique « EAX seul » | 10 | 82 659 | 36 |
| Candidat 2 | 0 | 82 659 | 0 |

Chaque exécution inclut 8 000 appels sur quatre threads. La contre-épreuve
supprime délibérément le contrôle d'EDX : elle reprend le principe de
classification de B7, **sans exécuter à nouveau le binaire B7 archivé**.

La série couvre les 4 095 erreurs, les états CF entrants, EDX arbitraire
pour les scalaires, les bornes `-4096/-4095/-1/0`, motifs signés/pointeurs,
retours larges ambigus, 14 arguments, restauration et alignement de pile,
masque du numéro, cases NULL et indices 599/600/65535. Ces combinaisons ne
sont pas toutes croisées exhaustivement. Les indices hors table sont omis
avec l'original, qui n'a pas de garde de borne.

Le vrai dispatcher est compilé avec des symboles dédiés dans le témoin ;
sa table privée ne remplace pas la bibliothèque système chargée. Un mini-stub
de test vérifie le résultat et errno. Il ne s'agit pas de la vraie routine
`cerror`, ni de son errno local au thread. Les appels concurrents testent
uniquement les retours scalaires synthétiques sans état partagé.

Les échecs de préparation sont conservés dans les preuves privées : lien
`libSystem` du SDK non résolu, chemins de sockets trop longs, `__TEXT` trop
bas pour Linux, puis LC_UNIXTHREAD sans démarrage crt. Le banc livré utilise
les bibliothèques de l'installation cohérente, des préfixes courts, la base
0x10000000 et LC_MAIN (minimum de lien 10.9). Ces échecs antérieurs n'entrent
pas dans les compteurs du protocole.

## Limites et prochaine étape

La convention réservée `-4095..-1` est déjà utilisée en x86_64 ; ce lot ne
prouve pas que tous les gestionnaires réels la respectent, notamment les
motifs de succès de psynch. Les motifs 64 bits de test ne qualifient pas le
comportement réel de `lseek`. La classification spéciale 199 doit être
réauditée si la table change. `thread_selfid` est déclaré `long` dans cette
source malgré son contrat Darwin large ; le relais `sys_syscall` retourne
`long`. Ces problèmes distincts restent ouverts.

**À FAIRE** : reconstruire `libsystem_kernel` dans un build indépendant,
comparer référence/candidat sur vrais appels avec positifs tous comptés,
ENOENT/EINVAL/ENOSYS, offsets 64 bits aux mots bas ambigus et errno/TLS en
concurrence ; identifier à nouveau les octets effectivement chargés.

Le même fichier source participe à `emulation` et `emulation_dyld` : une
reconstruction future peut donc aussi changer le dispatcher intégré à dyld.
Construire et qualifier ce dyld séparément. Aucun de ces résultats ne
qualifie QuickTime Player, Logic, EXS24 ou l'ensemble des appels BSD.

(44 fichiers). Leur transfert Windows, les SHA-256 et les huit comparaisons
d'octets V3 ont été vérifiés. Le manifeste public contient leurs empreintes
comme points de contrôle, sans fournir leurs binaires, logs ou chemins
personnels. Les fichiers protégés contrôlés avant/après sont identiques.
